# Authorization readiness — issue #92

Integration branch for optional REST authentication and consistent authorization.
This branch is stacked on the concurrency integration (#86), reviewed separately.

## Delivery order

- #93: per-operation access policies and explicit anonymous caller context.
- #94: item and collection read authorization.
- #95: persisted/proposed-state mutation authorization and upsert bypass prevention.
- #96: public/protected endpoint integration examples, tests and documentation.

Each child is implemented on its own branch and merged here after local tests.
Public endpoints remain supported, including anonymous reads with protected writes.
1.0 is the first compatibility baseline; no pre-1.0 migration layer is required.

## Validation

The implementation and local validation results are recorded below.

### #93 — explicit operation policies and typed contexts

Implementation `b892542`, fixture lint correction `cef4048`; Dart 3.13.7.
A default policy plus immutable per-operation overrides distinguishes public,
authenticated and custom access. Optional custom policies always receive an
explicit anonymous or verified caller. All operation contexts retain identity
and claims types; collection authorization must supply an explicit query scope.
Policy/verifier exceptions and denial cannot be turned into success by custom
exception mapping. Owned handlers and examples use the new API directly.

Passed:

- `dart tool/validation/validate.dart package dddart_rest --mode=local`
- `dart tool/validation/validate.dart consumer dddart_rest`
- `dart tool/validation/validate.dart example dddart_rest_example`

The package gate includes existing JWT/OAuth tests, all REST regressions, and a
fresh external consumer compiling/running native-identity contexts and concrete
claims/scope callbacks. Tests cover public CRUD, protected defaults, public GET
with protected writes, optional invalid credentials, anonymous custom hooks,
required custom hooks, concealment, policy errors and invalid configuration.
Mutation persistence still receives the additional atomic policy integration in
#95; this child establishes the final context/dispatch contract.

### #94 — item and collection visibility

Implementation `fe8edd5`; Dart 3.13.7. Response encoding and ETag construction occur
after item authorization. This intermediate revision used JSON value codecs for
policy snapshots; #96 replaced that strategy with an explicit complete domain
copier after proving that public projections can omit permission state. Added
read regressions cover stored
ownership, anonymous public objects, concealed/missing equivalence, every collection
request shape, thrown/denied policies, stricter query handlers, and application
scope applied to both rows and counts before pagination. Malicious tenant filters
cannot widen the verified tenant in the executable scoped-query fixture.

Passed `dart tool/validation/validate.dart package dddart_rest --mode=local`
and `dart tool/validation/validate.dart consumer dddart_rest`. The package lane
includes the external native-identity/typed-scope consumer and all existing

11 focused read tests pass. AUTH-002 will be reconciled with final integration
under #96, after mutation-policy integration is also complete.

### #95 — persisted-state mutation policy and create-only POST

Implementation `2383187`, generated-client 201 integration fix `d6c8592`.
Custom update/delete decisions use a coherent stored snapshot and an atomic
revision condition, including when the client supplies no header. A race returns
409 (implicit condition) or 412 (explicit condition), with no automatic retry.
POST uses create-if-absent, never an update, and a missing PUT also evaluates
create policy/normalization. Custom mutations on incapable repositories fail with
501; basic public/authentication-only CRUD remains available with its documented
concurrent-creation limitation. The ownership example uses the conditional
reference repository and checks current ownership, including deletion/transfer.

Passed with Dart 3.13.7:

- `dart tool/validation/validate.dart package dddart_rest --mode=local` — 328 tests.
- `dart tool/validation/validate.dart consumer dddart_rest`
- `dart tool/validation/validate.dart example dddart_rest_example`
- `dart tool/validation/validate.dart package dddart_repository_rest --mode=local` — 131 tests and clean external generation. The combined test caught the new 201 PUT-create response; generated ordinary saves now accept it.
- `dart test test/rest_concurrency_integration_test.dart` from the MySQL package — separate HTTP servers/connections still yield one atomic winner.

Regressions cover forged owner/tenant/role/publicity, legitimate edits and explicit
administrator transfer, POST overwrite and competing POST creation, preCreate,
missing-PUT create policy, loaded-state delete, anonymous custom mutations,
mutable detached snapshots, incapable backends, thrown policies, and ownership
changes after policy evaluation. Rejected/uncertain paths retain their events;
only committed writes publish/acknowledge. Existing UUID/native identity and media
contract tests passed against conditional storage where custom mutation policy
requires it.

### #96 — combined HTTP integration and final API

Integration `037c2a9`; final functional correction `2fcb218` and formatting
`b67f4bd`; API-comment corrections `db1a028`/`e57ff09`. Dart 3.13.7.
The real HTTP matrix contains 39 cases covering item, filtered/unfiltered and
pagination-only reads plus POST/PUT/DELETE with missing, allowed, denied and
invalid credentials. It also checks public reads/protected writes on one resource,
public objects with private scoped counts, owner/tenant forgery, existing-ID POST,
policy/verifier failures, and public CRUD without authentication configuration.

The registered finite `public_leaderboard_example.dart` runs the three required
scenarios without production credentials and closes its HTTP resources. The
ownership example, typed query documentation and request-flow description use
the final API. The obsolete prerelease migration guide was removed. AUTH-002 and
REST-004 are reconciled in `KNOWN_FRAMEWORK_DEFECTS.md`; the remaining event
limitations are explicitly left outside these two parents.

Final review exposed a real authorization bug in the intermediate snapshot
strategy: a response projection omitted Alice's owner field, reconstructed it as
Bob, and incorrectly allowed Bob's GET (expected 403, observed 200). Custom
aggregate policies now require `authorizationSnapshot`, a complete detached
domain copy independent of public JSON. The projection regression now returns
403, and construction rejects a missing copier. A copier returning the original
object or a different identity fails closed before policy/storage. Query-only
custom policies need no aggregate copier. Public/authentication-only resources
need no additional configuration. Applications remain responsible for copying
all permission state and mutable members; the framework cannot infer them from
a lossy public representation.
